# 01. Git 기초 — 프로젝트 폴더 생성과 GitHub 첫 Push와 커밋 수정

## 1. 이 작업은 무엇을 위해 시작했는가?

목표는 아무 코드도 없는 빈 폴더에서 직접 개발을 시작하고, 변경 이력을 내 Git 저장소에 기록한 뒤 GitHub에 올리는 것이었다. 이후 Spring Boot 앱을 만들고 첫 웹페이지를 띄우며, Docker Compose·MySQL·CRUD·테스트·CI/CD·AWS 배포 등 기능을 차례로 붙이는 출발점이다.

이번 Git 단위에서 실제로 다룬 흐름은 다음과 같다.

```text
빈 프로젝트 폴더
    ↓
로컬 Git 저장소 생성
    ↓
.gitignore와 README.md 작성
    ↓
이번 커밋에 넣을 변경을 선택(git add)
    ↓
로컬에 첫 커밋 저장(git commit)
    ↓
GitHub 원격 주소 등록(git remote add)
    ↓
첫 커밋을 GitHub에 업로드(git push)
    ↓
README 중복 문장 발견
    ↓
마지막 커밋을 수정된 커밋으로 교체(git commit --amend)
    ↓
GitHub의 기존 커밋을 교체(git push --force-with-lease)
```

여기서 중요한 점은, **파일을 생성하는 일, Git에 파일을 관리 대상으로 등록하는 일, 커밋으로 기록하는 일, GitHub에 올리는 일은 서로 다른 단계**라는 것이다. 이 차이를 이해하는 것이 이번 학습의 핵심이었다.

## 2. 개발 도구의 역할: IntelliJ, 터미널, Git, GitHub

### 2.1 IntelliJ IDEA와 터미널

**IntelliJ IDEA**는 Java를 비롯한 프로그램의 코드를 작성하고 실행·디버깅할 수 있는 **통합 개발 환경(IDE, Integrated Development Environment)**이다. 프로젝트 탐색기, 코드 편집기, 실행 버튼, 터미널 등의 기능을 하나의 프로그램에서 제공한다.

**터미널(Terminal)**은 명령을 입력하고 실행 결과를 확인하는 문자 기반 작업 창이다. Windows의 **PowerShell**은 이 터미널에서 사용할 수 있는 **셸(Shell)** 중 하나다. 셸은 사용자의 명령을 해석하고 OS로 전달/실행하는 프로그램이다.

이번 실습에서는 IntelliJ 하단의 `Terminal` 창을 사용했다. IntelliJ에서 터미널을 열었다고 해서 Git 명령이 특별한 IntelliJ 명령으로 바뀌는 것은 아니다. **그 안에서 Windows의 Git 프로그램을 실행한 것**이다.

작업 위치는 다음 경로였다.

```text
D:\myblog\myblog-portfolio
```

터미널에 `PS D:\myblog\myblog-portfolio>`와 같은 문자가 표시된다면, `PS`는 PowerShell, 뒤 경로는 현재 명령이 실행되는 작업 폴더를 뜻한다. 이 프롬프트 문자열은 명령어의 일부가 아니므로 그대로 입력하지 않는다.

터미널에서 다음 명령으로 설치 여부를 확인했다.

```powershell
git --version
```

- `git`: 컴퓨터에 설치된 Git 실행 파일을 호출한다.
- `--version`: 프로그램의 버전 정보를 출력하도록 요청한다.

이 명령은 파일을 만들거나 원격 서버에 접속하지 않는다.

### 2.2 Git과 GitHub는 같은 것이 아니다

**Git**은 파일의 변경 내용을 **커밋(Commit)**이라는 단위로 기록하고 비교·관리하는 **분산 버전 관리 시스템(Distributed Version Control System, DVCS)**이다. Git 자체는 인터넷 연결이나 GitHub 계정 없이도 로컬 컴퓨터에서 사용할 수 있다.

**GitHub**는 Git 저장소를 인터넷에서 호스팅하고 공유·협업할 수 있게 도와주는 원격 서비스다. GitHub는 Git의 기능을 이용하지만, Git 그 자체는 아니다.

이 차이가 왜 중요할까? 다음과 같은 일이 가능하기 때문이다.

- GitHub에 로그인하지 않고도 로컬에서 여러 번 `git commit`을 할 수 있다.
- 로컬에서 커밋한 내용이 GitHub에 **자동으로 올라가지는 않는다**.
- GitHub에 올라간 커밋을 다른 컴퓨터에서 가져와 작업할 수 있다.
- GitHub와 연결된 주소 설정을 지워도 로컬 커밋은 사라지지 않는다.

이번 실습에서는 먼저 Git으로 로컬 이력을 만들고, 나중에 GitHub를 연결했다.

## 3. 로컬 Git 저장소를 만든다는 것은 무슨 뜻인가?

### 3.1 폴더와 Git 저장소의 차이

일반 폴더에는 파일과 하위 폴더만 존재한다. 파일을 수정하더라도 Windows가 그 수정들을 Git 커밋으로 자동 기록하지는 않는다. 

이때 **로컬 Git 저장소(Local Git Repository)**는 Git이 그 프로젝트의 파일 변경과 커밋 이력을 관리할 수 있도록 준비된 디렉터리다. Git은 내부 메타데이터를 `.git` 디렉터리에 저장한다.

이번에는 빈 `D:\myblog\myblog-portfolio` 폴더에서 아래 명령을 실행했다.

```powershell
git init -b main
```

각 요소의 뜻은 다음과 같다.

| 요소 | 의미 |
| --- | --- |
| `git` | Git 실행 |
| `init` | 현재 폴더에 새로운 로컬 Git 저장소 초기화 |
| `-b main` | 초기 브랜치 이름을 `main`으로 지정 |

실행하면 Git이 현재 폴더 안에 `.git/`을 생성한다. **이미 존재하는 파일의 내용을 마음대로 수정하거나 GitHub에 업로드하는 명령이 아니다.**

### 3.2 `.git/`에는 무엇이 들어 있는가?

`.git/`은 Git의 **내부 관리 디렉터리**다. 커밋에 관한 데이터, 브랜치의 현재 위치, 원격 저장소 주소 설정 같은 정보를 보관한다. 일반적인 소스코드 파일과 목적이 다르다.

따라서 `.git/` 내부 파일을 개발자가 직접 수정해야 하는 경우는 드물다. 잘못 수정하거나 삭제하면 로컬 Git 이력을 정상적으로 사용할 수 없게 될 수 있다. `.git/`은 프로젝트의 변경 파일 목록에도 일반적인 `Untracked files`로 나타나지 않는다. Git이 자기 관리용으로 사용하는 특별한 디렉터리이기 때문이다.

### 3.3 `main` 브랜치는 무엇인가?

**브랜치(Branch)**는 Git의 커밋 이력에서 특정 작업 흐름의 현재 위치를 가리키는 이름이다. 기능 개발을 별도 브랜치에서 진행한 뒤 합치는 방식으로 활용할 수 있다.

지금은 다른 브랜치를 만들 필요가 없었다. 최초 개발 이력의 이름을 관례에 따라 `main`으로 정했다. 저장소를 초기화한 직후에는 아직 첫 커밋이 없으므로 `main`이라는 이름만 준비된 상태일 수 있다. 첫 커밋이 생성되면 그 브랜치가 실제 커밋을 가리키게 된다.

### 3.4 초기 상태를 보는 `git status`

```powershell
git status
```

**`git status`**는 현재 브랜치, 작업 파일의 변경, 커밋 대상으로 준비된 내용 등을 요약해 보여주는 명령이다. Git을 사용할 때 가장 자주 확인하는 명령 중 하나다.

초기에는 다음과 같은 정보가 나타날 수 있다.

```text
On branch main
No commits yet
```

이는 `main`에서 작업하고 있지만 아직 Git 이력에 기록된 커밋은 하나도 없다는 뜻이다. 오류가 아니다.

## 4. `.git/`, `.idea/`, `.gitignore`를 구분하기

### 4.1 갑자기 생긴 `.idea/`는 무엇인가?

실습 중 `git status`에 아래와 같은 메시지가 나타났다.

```text
Untracked files:
    .idea/
```

여기서 사용자가 제기한 질문은 다음과 같았다. **"`.git`과 비슷한 시간에 생긴 `.idea`는 뭔가요? 직접 설정하는 건가요? 삭제하면 어떻게 되나요?"**

**`.idea/`**는 Git이 아니라 **IntelliJ IDEA가 프로젝트별 설정을 저장하기 위해 관리하는 디렉터리**다. 프로젝트를 열거나 설정을 바꾸는 과정에서 자동 생성될 수 있다. 사용자가 일부 파일을 직접 작성할 필요는 일반적으로 없다.

예를 들어 IntelliJ에서 선택한 프로젝트 설정, 모듈 정보, 일부 실행 설정 등이 들어갈 수 있다.

`.idea/`를 삭제하면 Java 소스코드 자체가 삭제되는 것은 아니다. IntelliJ에서 프로젝트를 다시 열면 필요한 설정이 새로 생성될 수 있다. 그러나 **이전에 사용자가 선택한 실행 설정이나 개인화 설정까지 원래대로 복원된다고 보장할 수는 없다.** 따라서 별 이유 없이 삭제할 필요가 없다.

두 이름은 비슷해 보여도 전혀 다른 역할을 한다.

| 디렉터리 | 관리 주체 | 역할 |
| --- | --- | --- |
| `.git/` | Git | 로컬 Git 저장소의 이력과 설정 |
| `.idea/` | IntelliJ IDEA | IDE의 프로젝트 관련 설정 |

이 둘이 비슷한 시간에 생성된 것은 빈 프로젝트를 IntelliJ로 열고 Git도 초기화했기 때문일 수 있다. **Git 초기화가 `.idea/`를 만든다는 뜻은 아니다.**

### 4.2 `Untracked files`는 어떤 상태인가?

**추적되지 않는 파일(Untracked File)**이란 Git이 작업 폴더에서 발견했지만, **아직 Git의 커밋 이력에 포함하도록 관리된 적이 없는 파일**을 말한다.

초기 `Untracked files: .idea/`라는 문구는 "Git이 `.idea`를 찾았지만 아직 이력을 관리하지 않는다"는 의미다. 프로그램이 고장 나거나 파일이 손상됐다는 뜻이 아니다.

Git은 새로 만든 파일을 자동으로 전부 관리하지 않는다. 개발자가 어떤 파일을 기록하고 어떤 파일을 제외할지 결정할 수 있기 때문이다.

### 4.3 `.gitignore`는 어떤 파일인가?

**`.gitignore`**는 Git에 **무시할 파일·디렉터리의 패턴**을 알려주는 텍스트 설정 파일이다. 예를 들어 IDE가 자동 생성하는 설정, 빌드 결과물, 비밀값이 들어 있는 로컬 파일 등을 Git의 관리 대상에서 제외하는 데 사용한다.

이번 프로젝트에서 작성한 기본 규칙의 예시는 다음과 같다.

```gitignore
# IntelliJ IDEA 설정
.idea/
*.iml

# Gradle 캐시와 컴파일 결과물
.gradle/
build/

# 비밀값이 들어 있는 로컬 환경 파일
.env
```

- `#`으로 시작하는 줄은 사람이 읽는 설명용 **주석(Comment)**이다.
- `.idea/`는 프로젝트의 `.idea` 디렉터리를 무시한다.
- `*.iml`은 `.iml`로 끝나는 파일을 무시한다. `*`는 여러 이름과 대응할 수 있는 패턴 기호다.
- `.gradle/`은 Gradle 실행 중 만들어지는 로컬 캐시 디렉터리를 무시한다.
- `build/`는 컴파일과 테스트 과정에서 생성되는 빌드 결과물 등을 무시한다.
- `.env`는 비밀번호 등 로컬 환경 설정값을 담을 수 있으므로 원격 저장소에 실수로 올리지 않도록 제외한다.

주의할 점은 **`.gradle/`과 `gradle/`이 다르다**는 것이다. 나중에 Spring Boot 프로젝트를 만들 때 사용할 `gradle/wrapper` 같은 파일은 프로젝트의 재현 가능한 빌드에 필요하므로 대체로 커밋 대상이다. 이 폴더까지 `.gitignore`로 무시하지 않는다.

`.gitignore`를 만든 뒤 `git status`를 실행했을 때 `.idea/`가 Untracked 목록에서 사라지고 `.gitignore`만 남았다고 보고했다. 무시 규칙이 작동한 결과다.

### 4.4 `.gitignore`는 왜 자기 자신을 무시하지 않는가?

이것도 실습에서 직접 나온 질문이다. **"`.gitignore`는 `gitignore`에 기록하지 않는 건가요?"**

`.gitignore`는 이름 때문에 특별히 자동 제외되는 파일이 아니다. **무시 규칙을 기록하는 일반 파일이며 보통 Git으로 관리한다.**

예를 들어 개발자 A가 `.idea/`를 무시하도록 설정해 이 규칙을 커밋하고 GitHub에 올리면, 다른 개발자 B도 해당 저장소를 가져왔을 때 같은 무시 규칙을 사용할 수 있다. 팀이 공유해야 하는 설정이므로 기록할 가치가 있다.

따라서 `.gitignore`가 처음에는 `Untracked`로 표시되는 것도 자연스럽다. 이후 `git add .gitignore`를 실행하면 커밋 대상으로 준비할 수 있다.

### 4.5 `.gitignore`가 모든 보안 문제를 해결하지는 않는다

중요한 예외가 있다. **`.gitignore`는 이미 Git이 추적하고 있는 파일을 자동으로 추적 해제하지 않는다.**

예를 들어 과거에 실수로 비밀번호가 담긴 `.env`를 커밋했다면, 나중에 `.gitignore`에 `.env`를 추가하는 것만으로 과거 이력에서 비밀번호가 없어지는 것은 아니다. 이 경우에는 유출된 비밀번호를 교체하고, 필요하다면 별도의 이력 정리 절차를 검토해야 한다.

이번처럼 처음부터 `.env`를 무시하도록 만드는 것은 좋은 예방책이지만, **커밋 전 실제 포함 파일을 확인하는 습관**도 필요하다.

## 5. Git의 핵심 흐름: 작업 폴더 → 스테이징 → 커밋

### 5.1 왜 저장과 커밋 사이에 단계가 더 있는가?

가령 IntelliJ에서 `README.md`, `.gitignore`, Java 소스 세 파일을 한꺼번에 수정했다고 하자. 그런데 이번에는 README만 수정한 작업을 커밋하고 싶을 수 있다. Git이 모든 변경을 무조건 자동 커밋한다면 서로 관계없는 작업이 뒤섞인다.

그래서 Git은 개발자가 **이번 커밋에 담을 내용을 선택**하는 중간 단계를 제공한다.

### 5.2 작업 디렉터리(Working Directory)

**작업 디렉터리(Working Directory, Working Tree)**는 사용자가 실제 파일을 열고 작성·수정하는 공간이다. 이번 프로젝트에서는 `D:\myblog\myblog-portfolio` 안에 보이는 실제 파일들이 해당한다.

IntelliJ에서 README 문장을 편집하고 저장했다고 해서 Git 커밋이 즉시 생기지 않는다. 그 수정은 우선 작업 디렉터리의 파일 내용만 변경한다.

### 5.3 스테이징 영역(Staging Area, Index)

**스테이징 영역(Staging Area, Git Index)**은 **다음 커밋에 넣을 파일 내용의 버전을 Git 내부에 준비해 두는 영역**이다. '스테이징한다'는 말은 보통 `git add` 등을 이용해 이 영역에 내용을 등록한다는 뜻이다.

이번에는 아래 명령을 사용했다.

```powershell
git add .gitignore
```

이어서 README를 만든 뒤 다음 명령도 사용했다.

```powershell
git add README.md
```

여기서 `git add`의 `add`는 이름 때문에 혼동하기 쉽다. **이 명령은 GitHub에 업로드하는 것이 아니라, 현재 파일의 내용을 다음 커밋 대상으로 준비하는 것이다.** 아직 커밋이 완성된 것도 아니다.

Git은 스테이징된 버전을 내부적으로 기록한다. 파일을 실제 작업 폴더에서 다른 폴더로 이동시키는 것이 아니다.

스테이징된 파일은 `git status`에서 다음 영역에 나타난다.

```text
Changes to be committed:
    new file:   .gitignore
    new file:   README.md
```

이 문구는 "다음 `git commit`을 실행할 때 포함될 변경이 준비되어 있다"는 뜻이다.

#### 스테이징 이후 파일을 다시 수정하면?

**`git add README.md`를 실행한 다음 README를 한 번 더 수정해도, 나중에 수정한 부분까지 자동으로 스테이징되지는 않는다.**

예를 들어 다음 순서를 보자.

1. README에 `첫 번째 문장`이라고 작성한다.
2. `git add README.md`를 실행한다.
3. README를 다시 편집해 `두 번째 문장`을 추가한다.
4. 이 상태에서 곧바로 `git commit`한다.

이번 커밋에는 **3번에서 새로 추가한 내용이 빠질 수 있다.** 2번에서 선택한 파일 내용이 스테이징되어 있었기 때문이다. 3번의 변경까지 함께 담으려면 `git add README.md`를 다시 실행해야 한다.

이것이 스테이징을 **'파일 이름에 체크 표시만 하는 것'으로 이해하면 부족한 이유**다. 어떤 **파일 내용의 버전**이 등록됐는지가 중요하다.

### 5.4 커밋(Commit)

**커밋(Commit)**은 스테이징 영역에서 선택한 파일 상태를 **하나의 변경 이력으로 확정해 로컬 Git 저장소에 기록하는 것**이다.

첫 커밋을 위해 추천한 메시지와 명령은 다음과 같다.

```powershell
git commit -m "chore: 프로젝트 초기 설정"
```

- `git commit`: 준비된 내용을 새 커밋으로 기록한다.
- `-m`: 편집기를 따로 열지 않고 명령줄에서 커밋 메시지를 전달한다.
- 뒤의 따옴표 안 텍스트: 이 커밋이 어떤 작업인지 설명하는 메시지다.

처음으로 만든 커밋은 **루트 커밋(Root Commit)**이라고도 부른다. 그 이전에 부모 커밋이 없다는 의미다.

커밋이 생성되면 Git은 그 이력에 고유한 **커밋 ID(Commit Hash)**를 부여한다. 커밋을 구별하는 값이며, 커밋 내용과 메타데이터 등에 따라 결정된다. 설명 문장이 같더라도 나중에 Amend하면 커밋 ID가 달라지는 이유와 연결된다.

최신 커밋 하나를 확인하는 명령은 다음과 같다.

```powershell
git log -1 --oneline
```

- `log`: 커밋 이력을 출력한다.
- `-1`: 최근 한 개를 보여준다.
- `--oneline`: 커밋을 간단한 한 줄 형식으로 표시한다.

커밋 후 다음 상태가 나오면 현재 Git이 추적하는 파일에 미처리 변경이 없다는 뜻이다.

```text
nothing to commit, working tree clean
```

이 메시지는 모든 프로그램이 오류 없이 실행된다는 뜻은 아니다. **Git에 기록할 새로운 변경이 없다는 의미**다.

### 5.5 전체 상태를 한 번에 정리하면

| 구간 | 변경 내용이 있는 위치 | 사용한 작업 | GitHub에 반영됐나? |
| --- | --- | --- | --- |
| 파일 작성·저장 | 작업 디렉터리 | IntelliJ에서 파일 편집 | 아니요 |
| 커밋 대상으로 준비 | 스테이징 영역 | `git add` | 아니요 |
| 이력으로 확정 | 로컬 Git 저장소 | `git commit` | 아직 아니요 |
| 인터넷의 원격 저장소로 전송 | GitHub | `git push` | 예, 성공했다면 |

**저장 → 스테이징 → 커밋 → Push는 서로 다른 작업**이라는 점을 이해하면 이후 Git 오류 메시지를 훨씬 쉽게 읽을 수 있다.

## 6. 실제 한국어 커밋 메시지를 어떻게 정할 것인가?

실습 중 사용자는 **"AI가 만든 것 같은 과장된 영어 문장 말고, 실제 한국 개발자들이 쓸 법한 자연스러운 커밋 메시지"**를 원했다.

특정한 커밋 메시지 표준을 모든 한국 개발자가 사용하는 것은 아니다. 다만 이 개인 프로젝트에서는 **영어 타입 + 자연스러운 한국어 작업 설명**을 일관되게 사용하기로 했다.

기본 형식은 다음과 같다.

```text
타입: 실제 변경 내용
```

| 타입 | 의미 | 예시 |
| --- | --- | --- |
| `feat` | 새 기능 추가 | `feat: 게시글 등록 기능 구현` |
| `fix` | 버그 수정 | `fix: 게시글 수정 시 태그 누락 수정` |
| `refactor` | 외부 동작을 유지하며 내부 코드 구조 개선 | `refactor: 게시글 저장 로직 분리` |
| `test` | 테스트 코드 추가·수정 | `test: 게시글 서비스 테스트 추가` |
| `docs` | 문서 변경 | `docs: 로컬 실행 방법 정리` |
| `chore` | 프로젝트 관리·설정 작업 | `chore: 프로젝트 초기 설정` |
| `ci` | CI 설정·자동화 변경 | `ci: 푸시 시 테스트 실행 설정` |

여기서 타입은 Git 자체가 요구하는 문법이 아니라 **프로젝트에서 합의한 작성 관례**다. 처음에는 `feat:`, `fix:`처럼 짧게 쓰고, `feat(post):` 같은 세부 범위(scope)는 필요해질 때 도입하면 된다.

### 6.1 커밋을 얼마나 잘게 나눠야 하는가?

커밋을 작은 단위로 남기는 이유는 **각 변경을 이해하고 필요할 때 추적하기 쉽도록 하기 위해서**다. 커밋 개수를 늘려 보이게 하기 위해서가 아니다.

예를 들어 게시글 등록 기능과 그것을 검증하는 테스트가 하나의 작업으로 완성됐다면 다음처럼 한 커밋에 묶어도 자연스럽다.

```text
feat: 게시글 등록 기능 및 테스트 추가
```

반대로 한 줄 수정할 때마다 형식적인 커밋을 만드는 것은 학습이나 코드 리뷰에 도움이 되지 않을 수 있다. 지금은 **의미 있고 설명 가능한 변경 단위**를 우선한다.

기술적인 이유를 알기 위해서는 커밋 개수보다 **"이 커밋은 무엇을 바꾸었으며 왜 필요한가?"**라는 질문에 답할 수 있는지가 더 중요하다.

## 7. 로컬 저장소와 GitHub를 연결하기

### 7.1 원격 저장소(Remote Repository)란?

**원격 저장소(Remote Repository)**는 현재 작업 중인 내 컴퓨터 밖에 존재하는 Git 저장소다. GitHub에는 다음 주소로 생성했다.

```text
https://github.com/dideo233/myblog-portfolio
```

GitHub에서 새 저장소를 생성할 때 로컬에 이미 README와 `.gitignore`를 만들었으므로 GitHub 쪽에서는 별도의 README·`.gitignore`·라이선스를 자동 생성하지 않는다. 양쪽에 서로 다른 첫 커밋이 생기는 일을 피하기 위해서였다.

### 7.2 `git remote add`는 어디에 기록되나?

 `remote`로 원격 저장소를 등록했는데, 이는 GitHub 서버에 "연결 관계"를 설치하는 과정이 아니다. **원격 저장소 등록(Remote Configuration)**은 로컬 Git 저장소에 원격의 주소와 별명을 저장하는 작업이다. 

실습에서 사용한 명령은 다음과 같다.

```powershell
git remote add origin https://github.com/dideo233/myblog-portfolio.git
```

| 요소 | 의미 |
| --- | --- |
| `git remote` | 로컬 저장소의 원격 저장소 설정을 관리 |
| `add` | 새로운 원격 설정 추가 |
| `origin` | 원격 저장소를 가리키는 별명 |
| GitHub URL | 실제 원격 저장소 주소 |

**`origin`은 특별한 GitHub 서버 이름이 아니라 흔히 사용하는 별명**이다. URL을 매번 길게 적는 대신 `origin`이라는 이름으로 부를 수 있게 하는 것이다.

이 설정은 일반적으로 프로젝트의 **`.git/config`**에 보관된다. 예를 들면 다음과 비슷한 형태다.

```ini
[remote "origin"]
    url = https://github.com/dideo233/myblog-portfolio.git
    fetch = +refs/heads/*:refs/remotes/origin/*
```

이 파일은 원격 주소 등을 저장하는 Git의 로컬 설정이며, GitHub에 커밋되어 공유하는 일반 프로젝트 파일과는 다르다. `remote add`만 실행해서 커밋이나 파일이 GitHub에 올라가지는 않는다.

### 7.3 `git remote -v`가 왜 두 줄을 보여 주는가?

### 7.3. `git remote -v`가 왜 두 줄을 보여 주는가?

원격 저장소를 등록한 후 `git remote -v`를 실행하면 로컬 Git에 등록된 원격 저장소의 이름과 주소를 확인할 수 있다.

```text
origin  https://github.com/dideo233/myblog-portfolio.git (fetch)
origin  https://github.com/dideo233/myblog-portfolio.git (push)
```

같은 주소가 두 줄 출력되지만, **원격 저장소가 두 개라는 뜻은 아니다.** 하나의 원격 저장소인 `origin`에 대해 데이터를 가져올 때 사용할 주소와 보낼 때 사용할 주소를 각각 표시한 것이다.

여기서 **Fetch(페치)**와 **Push(푸시)**는 Git이 로컬 저장소와 원격 저장소 사이에서 데이터를 주고받는 서로 다른 작업이다.

- **Fetch (`git fetch`)**: 원격 저장소의 새로운 커밋과 관련 데이터를 로컬 Git 저장소로 가져오는 작업이다. 가져온 이력은 `.git` 내부에 저장되며, 현재 작업 중인 브랜치와 파일에 자동으로 반영되지는 않는다.
- **Push (`git push`)**: 로컬에서 기록한 커밋을 원격 저장소로 전송하는 작업이다. `git commit`으로 커밋을 만들었더라도 Push하지 않으면 GitHub에는 반영되지 않는다.

그렇다면 Fetch로 가져온 변경 사항을 실제 작업에 반영하려면 어떻게 해야 할까?

이때 사용하는 것이 **Merge(머지)**다. Merge는 서로 다른 브랜치의 변경 이력을 하나로 통합하는 작업이다.

예를 들어 로컬 `main` 브랜치에서 다음과 같이 실행할 수 있다.

```bash
git fetch origin
git merge origin/main
```

첫 번째 명령은 원격 저장소의 변경 이력을 가져오고, 두 번째 명령은 가져온 원격 `main`의 이력을 현재 로컬 `main`에 통합한다. 통합이 완료되면 필요한 파일 변경도 작업 폴더에 반영된다.

여기서 `origin/main`은 GitHub 서버의 브랜치 자체가 아니라, **마지막으로 fetch로 가져온 원격 `main`의 상태를 로컬에 기록한 원격 추적 브랜치(Remote-tracking Branch)**다.

이 두 과정을 간편하게 이어서 수행하는 단축 명령이 **Pull(풀)**이다.

```bash
git pull
```

Pull은 원격 변경을 Fetch한 뒤 현재 브랜치에 통합한다. 다만 Git 설정에 따라 Merge 대신 **Rebase(리베이스)** 방식으로 통합할 수도 있다. 간단히 말해 Rebase는 커밋을 다른 브랜치의 최신 이력 위에 다시 적용하는 방식이다.

정리하면 다음과 같다.

| 명령어 | 역할 |
|---|---|
| `git fetch` | 원격의 변경 이력을 가져오되 현재 작업에는 합치지 않는다. |
| `git merge` | 다른 브랜치의 변경 이력을 현재 브랜치에 통합한다. |
| `git pull` | 원격 변경 이력을 가져오고 현재 브랜치에 통합한다. |
| `git push` | 로컬에서 기록한 커밋을 원격 저장소로 보낸다. |

따라서 `git remote -v`에 나타나는 `(fetch)`와 `(push)`는 **하나의 원격 저장소에 대해 데이터를 가져오는 방향과 보내는 방향을 구분한 표시**다.

일반적인 개인 프로젝트에서는 두 작업에 동일한 GitHub 주소를 사용하므로 URL도 같지만, 필요에 따라 서로 다른 주소로 설정할 수도 있다.

### 7.4 원격 연결을 제거하거나 바꿀 수 있나?

```powershell
git remote remove origin
```

이 명령은 로컬 Git에 등록된 `origin` 원격 설정을 제거한다. **GitHub 저장소 자체를 삭제하지 않고, 이미 GitHub에 올린 파일도 삭제하지 않는다.** 현재 로컬에 남아 있는 커밋도 그대로다.

URL만 변경하고 싶다면 다음 형식의 명령이 있다.

```powershell
git remote set-url origin https://github.com/다른계정/다른저장소.git
```

원격의 주소를 바꾸는 것과 GitHub에서 실제 저장소를 삭제하는 것은 전혀 다른 작업이다. 이번 프로젝트에서는 연결이 정상적으로 설정됐으므로 변경할 이유가 없었다.

## 8. GitHub에 첫 커밋 올리기: `git push -u origin main`

실습에서는 원격 주소를 등록한 뒤 다음 명령으로 첫 Push를 진행했다.

```powershell
git push -u origin main
```

각 구성 요소의 의미는 다음과 같다.

| 요소 | 의미 |
| --- | --- |
| `git push` | 로컬 Git 커밋을 원격으로 전송 |
| `-u` | 로컬 브랜치와 원격 브랜치의 추적 관계(업스트림) 설정 |
| `origin` | 앞서 등록한 GitHub 원격 저장소의 별명 |
| `main` | Push하려는 로컬 브랜치 |

### 8.1 업스트림 브랜치(Upstream Branch)

**업스트림 브랜치(Upstream Branch)**는 로컬 브랜치가 비교·동기화 기준으로 삼도록 연결한 원격 쪽 브랜치다.

처음 Push할 때 `-u`를 붙여 로컬 `main`이 `origin/main`을 추적하도록 설정하면, 이후 현재 브랜치에서 다음과 같이 간단히 Push할 수 있다.

```powershell
git push
```

매번 원격 이름과 브랜치 이름을 전부 입력하지 않아도 되도록 **대응 관계를 기억한 것**이다. `-u`가 파일을 더 많이 업로드하거나 브랜치 이름을 특별하게 만드는 옵션은 아니다.

첫 Push에서 브라우저나 인증창이 열릴 수 있다. 이것은 GitHub에 전송할 권한이 있는지 확인하는 과정이다. 비밀번호·접근 토큰을 채팅에 그대로 붙여 넣을 필요가 없다.

### 8.2 Push가 끝나면 무엇이 달라지는가?

첫 Push가 성공하면 GitHub에 `.gitignore`, `README.md`, 커밋 이력이 나타난다. **이것은 로컬 Git에 이미 기록한 이력을 원격으로 전달한 결과**다.

새 저장소에 접속해 파일이 보이는지 확인할 수 있다.

## 9. 이미 Push한 첫 커밋의 README를 수정할 수 있을까?

결론부터 말하면 가능하다. 다만 **이미 공유한 Git 이력을 다시 쓰는 작업**이라는 차이가 있다.

### 9.1 일반 수정 커밋과 Amend의 차이

**새 수정 커밋을 추가하는 방법**은 기존 커밋을 그대로 두고, 그 뒤에 오타나 중복을 고친 새로운 커밋을 하나 더 만드는 것이다.

```text
첫 커밋 A: README 중복 있음
    ↓
수정 커밋 B: README 중복 제거
```

일반적인 협업 개발에서는 공유된 이력을 유지하기 때문에 이 방식이 안전하고 자연스럽다.

반면 **커밋 수정(Amend)**은 가장 최근 커밋을 새로운 내용으로 **다시 만들어** 대체하는 방법이다.

```text
기존 첫 커밋 A: README 중복 있음
         │
         └── Amend로 대체
                     ↓
새 첫 커밋 B: README 중복 제거
```

Git은 기존 커밋의 내용을 그 자리에서 직접 덮어쓰지 않는다. 새로운 커밋 B를 만들고 현재 브랜치가 그 커밋을 가리키도록 바꾸는 방식으로 동작한다. **따라서 커밋 수는 여전히 하나일 수 있지만, 커밋 ID는 A와 B가 다르다.**

또한 `git commit --amend`는 기본적으로 **가장 최근 커밋**에 작용한다. 오래전의 특정 커밋을 아무거나 지정해 수정하는 명령은 아니다.

### 9.2 실제 진행한 수정 흐름

먼저 IntelliJ에서 `README.md`의 중복 문장을 제거해 저장했다. 그 뒤 Git에서 수정 상태를 확인하고, 수정된 README 내용을 커밋 대상으로 다시 선택했다.

```powershell
git status
```

```powershell
git add README.md
```

그다음 최신 커밋을 교체하도록 다음 명령을 사용했다.

```powershell
git commit --amend --no-edit
```

- `git commit`: 커밋을 기록하는 명령이다.
- `--amend`: 방금 새 커밋을 뒤에 더하는 대신, **최신 커밋을 새 내용으로 대체**하도록 한다.
- `--no-edit`: 기존 커밋 메시지는 수정하지 않고 유지한다.

이때 준비된 내용이 README 수정뿐이라면 README를 반영한 새 첫 커밋이 만들어진다. **다른 변경도 스테이징되어 있으면 함께 포함될 수 있으므로 Amend 전에 `git status`를 확인하는 습관이 중요하다.**

교체된 커밋은 다음으로 확인할 수 있다.

```powershell
git log -1 --oneline
```

이 명령을 실행하기 전과 후의 커밋 해시가 서로 달라질 수 있다. 커밋 메시지가 같더라도 내용이 변경됐다면 새 커밋이기 때문이다.

### 9.3 왜 그냥 `git push`로는 안 되는가?

이미 GitHub에는 이전 첫 커밋 A가 올라가 있었다. 그런데 로컬 `main`은 Amend로 새 첫 커밋 B를 가리키게 됐다. 두 커밋은 같은 브랜치의 단순한 연속 커밋 관계가 아니다.

일반적으로 Git은 **원격 브랜치의 기존 이력을 자연스럽게 연장하지 않는 Push(Non-fast-forward Push)**를 거부한다. 다른 사람이 보고 있거나 작업 기준으로 삼은 커밋이 갑자기 사라지는 일을 막기 위해서다.

따라서 이번처럼 이미 Push한 커밋을 교체하려면 일반 Push와 다른 조치가 필요했다.

### 9.4 `--force-with-lease`는 무엇인가?

**`--force-with-lease`**는 Git에서 **이력을 교체하는 Push를 허용하되, 원격 브랜치가 내가 예상하는 상태에 있는지를 확인하는 안전장치**다.

```powershell
git push --force-with-lease origin main
```

구성 요소를 나누면 다음과 같다.

| 요소 | 의미 |
| --- | --- |
| `git push` | 로컬 커밋을 원격에 보내기 |
| `--force-with-lease` | 원격 상태가 예상과 맞을 때만 기존 이력을 교체하도록 허용 |
| `origin` | GitHub 원격 저장소 별명 |
| `main` | 변경할 원격 브랜치와 대응하는 로컬 브랜치 |

이 명령은 평소의 `git push`보다 강한 작업이다. 일반적인 `--force`보다 안전 조건이 있지만 **협업 중인 공유 브랜치에서 무조건 안전하다고 볼 수는 없다**. 원격 추적 정보가 다른 프로그램에 의해 갱신되는 상황 등에서도 주의가 필요하다.

이번 경우는 **개인이 새로 생성한 저장소의 첫 커밋 하나를 바로잡는 상황**이었으므로, 다른 사람이 그 커밋을 가져가 작업하지 않았다는 전제 아래 Amend와 Push를 학습할 수 있었다.

그러나 협업에서 여러 사람이 이미 사용하는 `main` 브랜치라면 대체로 **기존 커밋을 고쳐 쓰기보다 새 수정 커밋을 만들어 Push**하는 편이 적절하다. Git 이력을 예쁘게 만들겠다고 공유 이력을 함부로 교체해서는 안 된다.

### 9.5 Amend는 어떤 상황에서 쓰는가?

| 상황 | 보통의 선택 |
| --- | --- |
| 아직 Push하지 않은 마지막 커밋에 오타·누락 | Amend 적합 |
| 혼자 사용하는 새 저장소에서 바로 Push한 마지막 커밋 정리 | 위험을 확인한 후 Amend 가능 |
| 다른 사람이 이미 가져갔을 수 있는 커밋 수정 | 새 수정 커밋 권장 |
| 몇 개 전의 과거 커밋 수정 | 단순 `--amend`로 해결할 수 없음 |
| 기능 버그를 실제로 해결 | 보통 `fix:` 새 커밋 권장 |

이번 학습의 요점은 Amend를 자주 쓰라는 것이 아니라 **Git 커밋은 이력의 기록이며, 그 기록을 바꾸는 일과 새 이력을 추가하는 일이 다르다는 것**이다.

## 10. 파일을 만들고 기록할 때의 안전 원칙

### 10.1 실수로 저장소를 바꾸지 않기

`git init`과 `git add` 같은 명령은 **현재 어떤 폴더에서 실행하느냐**가 중요하다. `myblog-ex`, `myblog-portfolio` 두 로컬 저장소가 있다고 치면, 둘은 각각 이력을 관리하는 다른 프로젝트니 혼동하지 않는다.

### 10.2 커밋에 비밀값 넣지 않기

`.env`, DB 비밀번호, API 키, OAuth 비밀키 등은 실제 값이 GitHub에 올라가지 않도록 주의해야 한다. `.gitignore`는 유용한 예방책이지만 **추적되기 시작한 파일이나 과거 커밋의 비밀을 자동으로 지워 주지는 않는다.**

### 10.3 무엇이 커밋되는지 확인하기

다음 두 명령은 각각 목적이 다르다.

```powershell
git status
```

현재 변경 상태를 요약해 준다.

```powershell
git diff --cached
```

**스테이징 영역과 현재 커밋 사이의 차이**, 즉 다음 커밋에 들어갈 변경을 보다 구체적으로 보여준다. `--cached`는 `--staged`라는 이름으로도 사용할 수 있다. 이 명령은 파일을 수정하지 않는 조회 작업이다.

처음부터 모든 명령을 외울 필요는 없지만, **커밋하기 전에 정확히 무엇을 기록하는지 확인한다**는 습관을 만들 수 있다.

### 10.4 모든 수정이 Force Push를 필요로 하는 건 아니다

README 오타가 생겼다면 일반적으로는 수정한 뒤 새 커밋을 만들고 평범한 `git push`를 하면 된다. **Force Push는 이미 공개된 이력을 교체하겠다는 특별한 의도가 있을 때만 검토**해야 한다.
